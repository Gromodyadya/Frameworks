# Практическое занятие №2

## 1. Пояснение: Архитектура (Ядро и Модули)

Проект разделен на жесткий каркас и подключаемые плагины (согласно принципу Open-Closed Principle).

* **Что относится к ядру (Core):**
  Интерфейсы `IAppModule`, `IAppAction`, класс `ModuleCatalog` (загрузчик и сортировщик) и `Program.cs` (инициализатор). Ядро полностью абстрагировано от бизнес-логики. Его задачи: прочитать настройки, найти нужные DLL-сборки, извлечь из них модули, выстроить правильный порядок запуска с помощью топологической сортировки (алгоритм Кана) и запустить их.
* **Что относится к модулям (Plugins):**
  Файлы `ExportModule`, `LoggingModule`, `ReportModule`, `ValidationModule`, базовый `CoreModule` и авторский `MetricsModule`. Они содержат бизнес-правила (сохранение в файл, вывод метрик) и регистрируют свои зависимости в едином DI-контейнере.
* **Почему добавление нового модуля не требует редактирования логики запуска:**
  Ядро не имеет жестких ссылок (hardcode) на классы модулей. Оно использует механизм рефлексии (`Assembly.GetTypes()` и `Assembly.LoadFrom()`). Ядро динамически сканирует память программы и папку `/modules/` (реализовано усложнение [*]), находит все классы, наследующие контракт `IAppModule`, и создает их экземпляры. Для включения нового модуля (например, `MetricsModule`) достаточно просто дописать его имя в файл конфигурации `appsettings.json`.

## 2. Инструкция запуска

1. Откройте терминал в корневой папке проекта.
2. Для запуска автоматических тестов выполните:
   `dotnet test`
3. Для настройки активных модулей откройте файл `src/Pr2.ModulesAndDi/appsettings.json` и отредактируйте массив `"Modules"`.
4. Для запуска приложения выполните:
   `dotnet run --project src/Pr2.ModulesAndDi`

## 3. Набор проверок (Автоматизированные тесты)

В проекте (проект `Pr2.ModulesAndDi.Tests`) реализованы 4 модульных теста (xUnit), покрывающих базовые требования безопасности ядра:
1. **`Порядок_запуска_учитывает_зависимости`**: Проверяет математическую корректность топологической сортировки направленного ациклического графа (DAG).
2. **`Отсутствующий_модуль_даёт_понятную_ошибку`**: Проверяет, что при нехватке зависимости выбрасывается `ModuleLoadException`, а не происходит падение всей программы.
3. **`Цикл_зависимостей_обнаруживается`**: Проверяет защиту от бесконечных циклов (Deadlock) при инициализации.
4. **`Внедрение_зависимостей_работает`**: Доказывает, что сервисы (DI) создаются ядром и корректно передаются в `InitializeAsync`.

## 4. Демонстрационные сценарии с разными наборами модулей

Данные сценарии проверяются вручную путем редактирования файла `appsettings.json`.

### Сценарий 1: Запуск минимального набора модулей
* **Конфигурация `appsettings.json`:** `["Core", "Logging", "Metrics"]`
* **Ожидаемый результат:** Программа запускается успешно. Срабатывают только регистрация сервисов, логирование и сбор метрик. Никаких файлов экспорта или отчетов не создается.
* **Фактический результат:** В консоли выводится только "Проверка журнала событий" и "[МЕТРИКИ] Использовано памяти...".

### Сценарий 2: Запуск полного набора (Интеграционный Happy Path)
* **Конфигурация `appsettings.json`:** `["Core", "Logging", "Validation", "Export", "Report", "Metrics"]`
* **Ожидаемый результат:** Модули выстраиваются строго в порядке их зависимостей, указанных в свойстве `Requires`.
* **Фактический результат:** Алгоритм сортировки успешно выстраивает цепь. `Export` (требующий `Validation`) выполняется строго после проверки данных, а `Report` завершает цепочку. Система работает штатно.

### Сценарий 3: Запуск набора с пропущенной зависимостью
* **Конфигурация `appsettings.json`:** `["Core", "Export"]`
* **Описание:** Модуль `Export` требует для своей работы модули `Core` и `Validation`. Но мы намеренно "забыли" указать `Validation` в файле настроек.
* **Ожидаемый результат:** Ядро должно остановить запуск и сообщить о нехватке модуля.
* **Фактический результат:** Программа прерывается с исключением: `ModuleLoadException: Не хватает модуля для зависимости, модуль Export требует Validation`.

### Сценарий 4: Запуск набора с кольцевой зависимостью
* **Описание:** Намеренно изменяем исходный код: в `LoggingModule.cs` добавляем `Requires => new[] { "Validation" }`, а в `ValidationModule.cs` добавляем `Requires => new[] { "Logging" }`. Файл `appsettings.json` содержит оба модуля.
* **Ожидаемый результат:** Алгоритм Кана должен обнаружить, что граф нельзя отсортировать.
* **Фактический результат:** Приложение выбрасывает исключение: `ModuleLoadException: Обнаружена циклическая зависимость модулей, проблемные модули Logging, Validation`.
