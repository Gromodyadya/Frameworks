# Task2.FrameworkModules

## Что это за программа

`Task2.FrameworkModules` - это небольшая веб-служба на C# и ASP.NET Core. Она показывает, как можно сделать приложение, которое расширяется модулями без переписывания основной логики.

Главная идея работы такая: есть ядро программы, которое умеет запускаться, читать настройки, находить модули, проверять зависимости и собирать сервисы через DI-контейнер. А конкретное поведение вынесено в отдельные модули. Один модуль проверяет данные, второй строит отчет, третий экспортирует данные в CSV-файл.

То есть программа сделана не как один большой файл, где все связано напрямую, а как маленький каркас. В этот каркас можно добавлять новые расширения.

## Что умеет программа

Приложение умеет:

* читать список модулей из `appsettings.json`;
* загружать модули как внешние DLL из папки `modules`;
* проверять, что модуль поддерживает нужную версию контракта;
* строить правильный порядок запуска модулей по зависимостям;
* останавливать запуск с понятной ошибкой, если модуль отсутствует;
* останавливать запуск с понятной ошибкой, если зависимости образуют цикл;
* регистрировать сервисы модулей через DI-контейнер;
* выполнять обработку демонстрационных заказов через endpoint `POST /process`;
* создавать отчет и CSV-файл, если подключены соответствующие модули.

Реализованы три модуля:

* `Validation` - проверяет, что сумма заказа больше нуля;
* `Reporting` - формирует текстовый отчет по заказам;
* `Export` - сохраняет заказы в файл `orders.csv`.

Добавлены усложнения:

* загрузка модулей из отдельной папки как внешних библиотек;
* проверка совместимости версии контракта;
* демонстрация двух времен жизни объектов: `singleton` и `transient`.

`src/Task2.Contracts` - общий контракт. Его знают и ядро, и модули.

`src/Task2.Core` - логика каркаса: загрузка DLL, проверка зависимостей, сортировка модулей и запуск.

`src/Task2.Host` - сама веб-служба ASP.NET Core. Здесь создается приложение, читаются настройки и объявляются endpoints.

`README.md` - инструкция по запуску и отчет по работе.

`build.ps1` - скрипт сборки. Он собирает все проекты и копирует DLL модулей в папку `modules`.

## Основные файлы

`ModuleContract.cs` - описывает интерфейс `IAppModule`. Каждый модуль обязан иметь имя, список зависимостей, версию контракта, метод регистрации сервисов и метод инициализации.

`Services.cs` - содержит общие модели и интерфейсы сервисов: заказ, результат обработки, журнал, правило проверки, построитель отчета и экспортер.

`ModuleLoader.cs` - ищет DLL в папке `modules`, загружает их через reflection и находит классы, которые реализуют `IAppModule`.

`ModuleSorter.cs` - строит порядок запуска модулей. Если модуль зависит от другого, зависимость запускается раньше.

`ModuleRunner.cs` - вызывает у модулей два шага: сначала регистрацию сервисов, потом инициализацию.

`Program.cs` - точка входа веб-службы. Здесь читаются настройки, загружаются модули, настраивается DI-контейнер и создаются endpoints.

`HostServices.cs` - простые сервисы самого хоста: журнал запуска, часы для демонстрации `transient`, список загруженных модулей и тестовые заказы.

`ValidationModule.cs` - модуль проверки данных.

`ReportingModule.cs` - модуль отчета. В нем видно, что `IRequestClock` создается как `transient`.

`ExportModule.cs` - модуль экспорта. Он пишет CSV-файл и показывает `singleton`-сервис экспортера.

## Как работает запуск модулей

В `src/Task2.Host/appsettings.json` указан список модулей:

```json
{
  "Modules": [ "Validation", "Reporting", "Export" ],
  "ModuleDirectory": "modules",
  "ContractVersion": "1.0.0"
}
```

При старте происходит такая цепочка:

```text
Program.cs
-> ReadOptions()
-> ModuleLoader.Load()
-> загрузка DLL из modules
-> поиск классов IAppModule
-> проверка отсутствующих модулей
-> проверка версии контракта
-> ModuleSorter.Sort()
-> ModuleRunner.Register()
-> builder.Build()
-> ModuleRunner.InitializeAsync()
-> web API готово к работе
```

Если все модули подключены правильно, порядок получается такой:

```text
Validation -> Reporting -> Export
```

Такой порядок нужен, потому что:

* `Reporting` зависит от `Validation`;
* `Export` зависит от `Reporting`;
* значит, `Export` нельзя запускать первым.

## Как работает запрос

Например, пользователь отправляет запрос:

```text
POST /process
```

Дальше происходит такая цепочка:

```text
HTTP request
-> endpoint POST /process
-> получение тестовых заказов
-> получение всех IDataRule из DI
-> проверка заказов
-> получение IReportBuilder из DI
-> построение отчета
-> получение IDataExporter из DI
-> экспорт CSV
-> HTTP response
```

Если модуль `Validation` подключен, в контейнере есть правило проверки `PositiveAmountRule`.

Если модуль `Reporting` подключен, в контейнере есть `IReportBuilder`, и программа строит отчет.

Если модуль `Export` подключен, в контейнере есть `IDataExporter`, и программа создает файл `orders.csv`.

## Какие части относятся к ядру, какие к модулям

К ядру относятся:

* `Task2.Contracts` - общий контракт и интерфейсы;
* `Task2.Core` - загрузчик модулей, сортировщик зависимостей, запуск модулей;
* `Task2.Host` - веб-служба, чтение настроек, endpoints и базовые сервисы хоста.

К модулям относятся:

* `Task2.ValidationModule` - добавляет проверку заказов;
* `Task2.ReportingModule` - добавляет построение отчета;
* `Task2.ExportModule` - добавляет экспорт в CSV.

Добавление нового модуля не требует редактирования логики запуска, потому что ядро работает только через интерфейс `IAppModule`. Оно не знает классы `ValidationModule`, `ReportingModule` и `ExportModule` напрямую. Ядро просто загружает DLL из папки, ищет внутри реализации `IAppModule`, читает имя модуля и зависимости, а потом вызывает стандартные методы `RegisterServices` и `InitializeAsync`.

Чтобы добавить новый модуль, нужно:

1. создать новый проект библиотеки;
2. реализовать `IAppModule`;
3. зарегистрировать свои сервисы в `RegisterServices`;
4. собрать DLL;
5. положить DLL в `src/Task2.Host/modules`;
6. добавить имя модуля в `appsettings.json`.

Код `ModuleLoader`, `ModuleSorter` и `ModuleRunner` при этом менять не надо.

## Пояснение к программе

DI-контейнер нужен здесь для того, чтобы модули не создавали зависимости вручную. Например, `ReportBuilder` не делает `new PositiveAmountRule()`. Вместо этого он получает все `IDataRule` из контейнера. Поэтому один модуль может добавить правило проверки, а другой модуль сможет использовать это правило через интерфейс.

Reflection используется в `ModuleLoader.cs`. Это механизм C#, который позволяет во время выполнения открыть DLL и посмотреть, какие типы внутри нее есть. Благодаря этому хост не ссылается напрямую на проекты модулей.

Топологическая сортировка используется в `ModuleSorter.cs`. Простыми словами, это способ расположить модули так, чтобы каждая зависимость стояла раньше того модуля, которому она нужна.

Версия контракта нужна для безопасности запуска. Если случайно положить в папку DLL от старой или несовместимой версии задания, приложение не должно молча запускать ее.

## Правила проверки данных

В демонстрационной области есть заказы:

```text
Id, Customer, Amount
1, Ada, 1200
2, Grace, 850
3, Linus, 430
```

Модуль `Validation` проверяет, что `Amount` больше нуля. Если появится заказ с нулевой или отрицательной суммой, endpoint вернет ошибку `BadRequest` со списком сообщений.

## Как проверить ошибки модулей вручную

Список модулей можно менять в `src/Task2.Host/appsettings.json`.

Примеры:

| Сценарий | Настройка `Modules` | Результат |
| --- | --- | --- |
| Полный запуск | `[ "Validation", "Reporting", "Export" ]` | Работают проверка, отчет и экспорт |
| Только проверка | `[ "Validation" ]` | Работает только проверка |
| Нет зависимости | `[ "Export" ]` | Ошибка `Missing module 'Reporting'` |
| Несуществующий модуль | `[ "Validation", "Unknown" ]` | Ошибка `Missing configured module(s): Unknown` |

Цикл зависимостей удобнее проверять автоматическим тестом, потому что рабочие модули специально написаны без цикла.

* корректный порядок запуска на цепочке зависимостей;

## Экспериментальная часть

В работе менялся набор модулей и проверялось поведение программы.

При полном наборе модулей приложение запускается в порядке:

```text
Validation -> Reporting -> Export
```

При отсутствии нужной зависимости приложение не продолжает работу, потому что запуск в неправильном порядке мог бы привести к ошибкам дальше.

При циклической зависимости приложение тоже останавливается. Это правильное поведение, потому что невозможно решить, какой модуль запускать первым, если они требуют друг друга.

Также проверено, что DI действительно используется. В тесте `InjectsDependencies` объект `NeedsLog` получает `IRunLog` через конструктор. Если бы контейнер не создавал зависимости, этот тест не прошел бы.

## Риски и ограничения

Данные в программе демонстрационные и хранятся в коде. Это нормально для учебного задания, но для настоящей системы нужна база данных.

Модули загружаются из локальной папки без цифровой подписи. В реальном проекте нужно было бы проверять источник DLL и права доступа к папке.

CSV-файл перезаписывается при каждом вызове `POST /process`. Для демонстрации этого достаточно, но в реальной системе лучше добавлять уникальные имена файлов или хранить историю экспортов.

В проекте нет авторизации, потому что задание про модули, DI и порядок запуска, а не про пользователей и права доступа.

## Короткий итог

В результате получилась мини веб-служба с расширяемым модульным каркасом. Ядро отвечает за запуск, настройки, загрузку DLL, проверку зависимостей и DI. Модули отвечают только за свое прикладное поведение: проверку, отчет и экспорт.

Главный результат работы: новое поведение можно добавлять отдельной DLL, не переписывая механизм запуска приложения.
