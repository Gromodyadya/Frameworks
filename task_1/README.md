# TaskCatalog.Api

## Что это за программа

`TaskCatalog.Api` - это небольшая веб-служба на C# и ASP.NET Core. Она имитирует каталог учебных задач студента.

Главная цель работы - показать, как запрос проходит через конвейер обработки: сначала попадает в приложение, затем проходит через общие обработчики, после этого доходит до конкретного маршрута и в конце превращается в HTTP-ответ.

Пример предметной области простой: есть учебные задачи. У каждой задачи есть название, курс, сложность, признак выполнения, примечание и дата создания.

## Что умеет программа

Приложение хранит данные в памяти процесса, то есть без базы данных. Пока сервер запущен, созданные задачи доступны. После перезапуска данные снова становятся начальными.

Реализованы основные точки доступа:

* `GET /api/items` - получить список учебных задач.
* `GET /api/items/{id}` - получить одну задачу по идентификатору.
* `POST /api/items` - создать новую задачу.
* `GET /api/logs` - посмотреть журнал последних запросов.

Также добавлены усложнения:

* фильтрация списка по курсу, выполнению и сложности;
* сортировка списка;
* ограничения длины входных данных;
* потокобезопасное создание задач;
* единый формат ошибок;
* журналирование запроса и ответа;
* измерение времени обработки запроса.

## Основные файлы

`Program.cs` - точка входа приложения. Здесь создается ASP.NET Core приложение, подключаются сервисы, middleware и маршруты.

`Models.cs` - модели данных: учебная задача, запрос на создание, параметры поиска, ошибка и запись журнала.

`TaskStore.cs` - хранилище задач в памяти. Здесь находятся операции получения списка, поиска по `id` и создания задачи.

`TaskValidator.cs` - проверка входных данных. Например, название не должно быть пустым, сложность должна быть от 1 до 5.

`Middleware.cs` - три обработчика конвейера:

* `ExceptionHandlingMiddleware` ловит ошибки и превращает их в понятный JSON-ответ;
* `RequestLoggingMiddleware` пишет информацию о запросе и ответе;
* `TimingMiddleware` измеряет время выполнения запроса.

`RequestLogStore.cs` - хранит последние записи журнала в памяти.

`AppException.cs` - специальное исключение приложения. Оно содержит HTTP-статус и код ошибки.

## Как работает запрос

Например, пользователь отправляет запрос:

```text
GET /api/items/999
```

Дальше происходит такая цепочка:

```text
HTTP request
-> ExceptionHandlingMiddleware
-> RequestLoggingMiddleware
-> TimingMiddleware
-> endpoint GET /api/items/{id}
-> TaskStore.Get(id)
-> HTTP response
```

Если задача найдена, приложение возвращает JSON с задачей.

Если задачи нет, `TaskStore` выбрасывает `AppException` с кодом `ITEM_NOT_FOUND`. Это исключение ловит `ExceptionHandlingMiddleware` и возвращает единый ответ:

```json
{
  "errorCode": "ITEM_NOT_FOUND",
  "message": "Item 999 was not found.",
  "requestId": "0HNL..."
}
```

`requestId` нужен, чтобы связать ошибку у клиента с записью в журнале сервера.

## Почему маршрутизация и конвейер сделаны как аккуратный каркас

Маршрутизация отвечает только за то, какой сценарий выполнить для конкретного URL. Например, `GET /api/items` означает "вернуть список", `POST /api/items` означает "создать элемент". В маршрутах нет лишней инфраструктурной логики: они не занимаются общим журналированием, не измеряют время и не форматируют все ошибки вручную.

Конвейер middleware отвечает за общие действия, которые нужны почти каждому запросу. Ошибки обрабатываются в одном месте, поэтому все ответы об ошибках имеют одинаковую форму. Логирование тоже находится в одном месте, поэтому не нужно копировать запись в журнал в каждый endpoint. Измерение времени вынесено в отдельный обработчик, потому что это сквозная техническая задача, а не правило предметной области.

Такой подход выглядит как каркас, потому что у каждой части есть своя роль:

* маршруты описывают внешний API;
* хранилище отвечает за данные;
* валидатор отвечает за правила предметной области;
* middleware отвечает за общую обработку запроса;
* модели задают форму данных.

Если проект будет расти, можно добавлять новые маршруты и новые правила, не переписывая весь конвейер. Например, можно добавить `PUT /api/items/{id}` или заменить in-memory хранилище на базу данных, а обработка ошибок и логирование при этом останутся теми же.

## Использованные паттерны

`Middleware` - запрос проходит через несколько общих обработчиков: ошибки, логи и время; это в `Middleware.cs` и `Program.cs`.

`Dependency Injection` - нужные объекты не создаются вручную, а автоматически передаются туда, где нужны; это в `Program.cs`.

`Repository` - вся работа со списком задач лежит в одном месте; это `TaskStore.cs`.

`DTO` - отдельная модель для данных, которые пользователь отправляет при создании задачи; это `CreateStudyTaskRequest` в `Models.cs`.

`Validator` - отдельно проверяет, правильно ли заполнены данные задачи; это `TaskValidator.cs`.

`Единый формат ошибок` - все ошибки возвращаются одинаково: код, сообщение и requestId; это `AppException.cs`, `Middleware.cs`, `Models.cs`.

`Singleton` - один общий объект хранит задачи во время работы программы; это настроено в `Program.cs`.

`Lock` - не дает нескольким запросам одновременно испортить список или выдать одинаковый id; это `TaskStore.cs`.

`Test Runner` - отдельная программа запускает API и проверяет, что все работает; это `tests/TaskCatalog.Tests/Program.cs`.

## Правила валидации

При создании задачи проверяются входные данные:

* `title` обязателен;
* `title` не длиннее 80 символов;
* `course` обязателен;
* `course` не длиннее 60 символов;
* `difficulty` должен быть от 1 до 5;
* `notes` не длиннее 250 символов.

Если данные некорректные, API возвращает ошибку `VALIDATION_ERROR`.

## Параметры списка

`GET /api/items` можно вызывать с параметрами:

* `course` - фильтр по части названия курса;
* `completed` - фильтр по выполнению: `true` или `false`;
* `minDifficulty` - минимальная сложность;
* `maxDifficulty` - максимальная сложность;
* `sort` - сортировка.

Допустимые значения `sort`:

* `title` - по названию по возрастанию;
* `-title` - по названию по убыванию;
* `difficulty` - по сложности по возрастанию;
* `-difficulty` - по сложности по убыванию;
* `-created` - сначала новые.

Пример:

```text
GET /api/items?course=Frameworks&sort=-difficulty
```

Этот запрос вернет задачи курса `Frameworks` и отсортирует их по сложности от большей к меньшей.

## Как запустить программу

Откройте PowerShell в папке проекта:

```powershell
cd C:\progects\Frameworks\task_1
```

Сначала задайте переменные окружения:

```powershell
$env:DOTNET_CLI_HOME='C:\progects\Frameworks\task_1\.dotnet'
$env:APPDATA='C:\progects\Frameworks\task_1\.appdata'
$env:NUGET_PACKAGES='C:\progects\Frameworks\task_1\.nuget\packages'
```

Эти переменные нужны, чтобы .NET использовал служебные папки внутри проекта. Это удобно для учебной и ограниченной среды: сборка не зависит от настроек профиля пользователя.

Восстановите проект:

```powershell
dotnet restore tests\TaskCatalog.Tests\TaskCatalog.Tests.csproj --configfile NuGet.Config
```

Эта команда подготавливает проекты к сборке.

Запустите API:

```powershell
dotnet run --project src\TaskCatalog.Api\TaskCatalog.Api.csproj --urls http://127.0.0.1:5107
```

После запуска веб-служба будет доступна по адресу:

```text
http://127.0.0.1:5107
```

Окно PowerShell с запущенным сервером нужно оставить открытым. Чтобы остановить сервер, нажмите `Ctrl+C`.

## Как проверить вручную

Откройте второе окно PowerShell и выполните запрос списка:

```powershell
Invoke-RestMethod http://127.0.0.1:5107/api/items
```

Создайте новую задачу:

```powershell
Invoke-RestMethod `
  -Uri http://127.0.0.1:5107/api/items `
  -Method Post `
  -ContentType 'application/json' `
  -Body '{"title":"Prepare defense","course":"Frameworks","difficulty":4,"notes":"Manual check"}'
```

Получите задачу по идентификатору:

```powershell
Invoke-RestMethod http://127.0.0.1:5107/api/items/1
```

Проверьте фильтрацию и сортировку:

```powershell
Invoke-RestMethod http://127.0.0.1:5107/api/items?course=Frameworks`&sort=-difficulty
```

Проверьте журнал запросов:

```powershell
Invoke-RestMethod http://127.0.0.1:5107/api/logs
```

Проверьте ошибку для несуществующего элемента:

```powershell
Invoke-RestMethod http://127.0.0.1:5107/api/items/99999
```

В этом случае PowerShell может показать ошибку HTTP, потому что сервер вернет статус `404`. Это нормальное поведение. В теле ответа будет единый формат ошибки с `errorCode`, `message` и `requestId`.

## Экспериментальная часть

В эксперименте менялся тип запроса: получение списка, создание элемента, чтение по `id`, запрос несуществующего элемента, фильтрованный список.

Наблюдались такие результаты:

* HTTP-статус ответа;
* структура JSON-ответа;
* наличие `requestId`;
* наличие записи в журнале;
* наличие времени обработки запроса.

Результат: все проверенные сценарии воспроизводимо возвращают ожидаемую форму ответа. Для каждого обработанного запроса в журнале есть идентификатор и время выполнения. Это значит, что ошибку можно связать с конкретной записью на стороне сервера.

## Риски и ограничения

Данные хранятся в памяти, поэтому они пропадают после перезапуска приложения. Для учебного задания это нормально, но для реальной системы нужна база данных.

Приложение не содержит авторизации. В реальном проекте нужно было бы добавить проверку пользователя и права доступа.

Размер входных строк ограничен, чтобы пользователь не мог отправить слишком большие данные. Ошибки не раскрывают stack trace клиенту, поэтому внутренние детали приложения не показываются наружу.

На Windows отключены системные лог-провайдеры и оставлен console logging. Это сделано потому, что запись в Windows Event Log может требовать повышенных прав и ломать запуск в ограниченной среде.

## Ответы на контрольные вопросы для защиты

1. Что является независимой и зависимой переменной?

Независимая переменная - это тип и параметры HTTP-запроса. Например, можно отправить успешный `GET /api/items`, создать элемент через `POST /api/items`, запросить несуществующий `id` или добавить параметры фильтрации. Зависимые переменные - это результат работы системы: HTTP-статус, тело ответа, запись в журнале и время обработки.

2. Какие угрозы валидности есть у эксперимента и как они уменьшались?

Главные угрозы валидности - маленький набор тестовых данных, локальный запуск без настоящей нагрузки и отсутствие внешней базы данных. Эти угрозы уменьшены тем, что проверки автоматизированы и покрывают разные сценарии: успешное создание, чтение, ошибку `404`, валидацию, фильтрацию, сортировку и журналирование. Команды запуска зафиксированы, поэтому другой человек может повторить проверку.

3. Какая часть решения должна быть в ядре каркаса, а какая на стороне приложения?

В ядре каркаса должны быть маршрутизация, middleware-конвейер, общий формат ошибок, журналирование и измерение времени. Эти механизмы одинаково полезны для разных предметных областей. На стороне приложения должны оставаться конкретные модели, правила валидации и хранилище задач, потому что они зависят от выбранной предметной области.

4. Какие типовые ошибки или антипаттерны обнаружены в процессе реализации?

Первый антипаттерн - писать обработку ошибок отдельно в каждом endpoint. Тогда формат ошибок быстро становится разным. Второй - смешивать в маршруте всю логику: проверку данных, хранение, логирование и формирование ошибок. Третий - выдавать идентификаторы без защиты при параллельных запросах. Четвертый - возвращать клиенту технические исключения вместо понятного сообщения.

5. Как изменились бы выводы, если бы масштаб системы вырос в десять раз?

При росте системы in-memory хранилище стало бы слабым местом: данные нужно было бы перенести в базу данных. Журнал лучше отправлять в централизованную систему логирования. Также понадобились бы нагрузочные тесты, авторизация, пагинация списка, более строгая схема ошибок и разделение проекта на слои. Но сама идея каркаса сохранилась бы: маршруты отвечают за API, middleware - за общую обработку, доменная логика - за правила предметной области.

## Короткий итог

Эта работа показывает минимальный, но цельный каркас веб-службы. Запрос не обрабатывается случайным набором функций: он проходит через понятный конвейер, затем попадает в нужный маршрут, использует отдельное хранилище и отдельную валидацию, а ошибки и журналирование выполняются единообразно для всего приложения.
