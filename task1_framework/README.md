# Практическое задание 1: Каталог учебных задач

## Архитектурное пояснение
В проекте реализован паттерн "Конвейер" (Middleware) в ASP.NET Core. 
Выбранный способ маршрутизации и обработки выглядит как аккуратный каркас, потому что:
1. **Разделение ответственности:** Бизнес-логика (в `Program.cs`) не знает о логировании или перехвате ошибок. Она занимается только проверкой данных и сохранением.
2. **Сквозной функционал вынесен в ядро:** `TimingAndLogMiddleware` и `ErrorHandlingMiddleware` оборачивают каждый запрос. Это избавляет код от дублирования блоков `try-catch` и `Stopwatch` в каждой точке доступа.
3. **Безопасность параллельных запросов:** Использован `ConcurrentDictionary`, что защищает данные от порчи (race conditions) при одновременных POST-запросах.

## Инструкция по запуску
1. Открыть терминал в папке проекта.
2. Выполнить команду: `dotnet run`
3. Сервер запустится на `http://localhost:5000` (порт может отличаться, см. консоль).

## Сценарии проверки (команды для консоли PowerShell)

1. Создание задачи (Успех):
Invoke-RestMethod -Uri "http://localhost:54255/api/items" -Method Post -Headers @{"Content-Type"="application/json"} -Body '{"title":"Изучить Middleware", "difficulty": 7}'

2. Проверка валидации (Ошибка 400 - неверная сложность):
Invoke-RestMethod -Uri "http://localhost:54255/api/items" -Method Post -Headers @{"Content-Type"="application/json"} -Body '{"title":"Простая задача", "difficulty": 99}' -SkipHttpErrorCheck

3. Получить все задачи:
Invoke-RestMethod -Uri "http://localhost:54255/api/items" -Method Get

4. Получить несуществующий элемент (Ошибка 404):
Invoke-RestMethod -Uri "http://localhost:54255/api/items/11111111-1111-1111-1111-111111111111" -Method Get -SkipHttpErrorCheck

## Ответы на контрольные вопросы
1. **Независимая переменная:** Входящие данные HTTP-запроса (JSON тела, метод, URL). **Зависимая переменная:** Время обработки запроса, HTTP статус ответа и запись в журнале логов.
2. **Угрозы валидности:** Сетевые задержки при замере времени (нивелировано замером внутри Middleware через Stopwatch, а не на клиенте), порча данных при конкурентных запросах (нивелировано использованием `ConcurrentDictionary`).
3. **Разделение решения:** В ядре каркаса (Middlewares) должны быть сквозные вещи: логирование, генерация RequestId, перехватчик Exception. На стороне приложения (Endpoints, Services) должна оставаться бизнес-логика: правила валидации предметной области, сохранение в хранилище.
4. **Типовые ошибки/Антипаттерны:** 1) Дублирование `try-catch` в каждом методе API вместо единого обработчика. 2) Использование обычного `Dictionary` вместо `ConcurrentDictionary` в многопоточной веб-среде.
5. **Масштабирование в 10 раз:** Хранение в памяти (`InMemoryItemRepository`) перестанет подходить. Потребуется заменить его реализацию на работу с базой данных (например, PostgreSQL). Для распределенной системы обычного `RequestId` будет мало, потребуется полноценный Distributed Tracing (OpenTelemetry), чтобы отслеживать запрос между микросервисами.
